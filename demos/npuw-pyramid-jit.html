NPUW Pyramid JIT

Growing an NPU KV cache without paying for it up front · Qwen2.5-3B INT8 · Intel NPU 5 · OpenVINO 2026.3

An NPU cannot resize a KV cache, so growing context means compiling a second model and switching to it mid-decode. That works, but compiling every capacity up front costs 5.4× more than compiling one. Improvement 2 compiles the next capacity during decode instead — and the compile finishes with 20 minutes to spare.

Does the mechanism cost anything?

The mechanism is practical. Splitting the model by capacity does not cost throughput (0.8% in B1's favour overall), and the switch is a bounded one-off. What it does cost is compile: 3,503 s against 651 s, all of it before the first token. That is the number Improvement 2 attacks.

Improvement 2 — compile during decode

One-ahead JIT compiles only the first capacity up front. The next one is compiled in the background while decode runs on the current one, and must be ready before the cache fills. Measured end to end on 1024→2048, against an eager control that compiles both first.

Decode costs 3.6 ms more per token (0.26%) while the background compile runs. The boundary logits are byte-identical to the eager control at both capacities (max abs difference 0.0, all 1,920 tokens aligned), so hiding the compile changed nothing about the output.

The slack is the headline: the 2048 variant was ready 20 minutes before the switch needed it. On this model a capacity compile costs ~15 s and buys ~20 minutes of decode, so the schedule has room for the larger jumps this run did not test (2048→4096 upward).
