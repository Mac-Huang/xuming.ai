NPUW Pyramid JIT — the eager control

Qwen2.5-3B INT8 on the Intel NPU · OpenVINO 2026.3 · wuklab-NUC16 · run 2026-08-17

An NPU cannot resize a KV cache. To grow context you compile a second model at the larger capacity and switch to it mid-decode. This run compiles both up front so the switch never waits. It is the control: it prices the switch with compile time removed, so a later lazy run can be charged for exactly what it adds.

What the run does

The pyramid holds two compiled copies of the same model, one per KV capacity: 1024 and 2048. Decode starts on the 1024 copy. At token 895 the cache is full, so the runtime moves the live KV into the 2048 copy and carries on. That move is the copy_on_grow path.

The workload is fixed so nothing drifts: a 128-token prefill, then 1920 teacher-forced tokens (always token 42), so every step does identical work and the only thing that changes is the cache.

The timeline

The two variants finish compiling 21 minutes before the switch needs the second one. The native profile records that slack directly: readiness_slack_s = 1,263.9, wait_us = 0.0. Zero stall. That is the whole point of the control arm.

Compile cost does not track capacity

This matters for the lazy version. If compiling the 2048 variant were much more expensive than the 1024 one, deferring it would be risky. It is not: the second variant costs about 12.7 s to build, and that is the budget a lazy run has to hide behind 895 decode steps — roughly 20 minutes of cover for 13 seconds of work.

Decode, token by token

Decode runs at 1,348.0 ms per token (0.741 tok/s) and stays there. The distribution is tight — p95 is 1.5% above p50 in the first band. Nothing is competing for the device, which is what you expect when no compilation is running in the background.

Doubling the cache costs almost nothing

That is +0.9% for 2× the capacity. Decode here is bound by streaming the weights, not by walking the cache, so the larger cache barely registers. The practical reading: capacity headroom is cheap to hold, and the pyramid does not pay a running tax for having grown.

What the switch actually costs

The copy is not the cost. Moving the live KV — 36 tensor pairs, 36.0 MiB, 71.9 MiB of CPU traffic — takes 18.8 ms. Building the new infer request takes 391.5 ms, or 91% of the accounted switch.

So the obvious optimisation is not a faster copy. It is creating the larger request earlier — it depends on nothing but the compiled variant, which was ready 21 minutes before. Doing that would remove most of the spike.

One number is not explained. The switch profile accounts for 428.9 ms, but the token ran 764.3 ms over baseline — a gap of about 335.3 ms. The first inference on a freshly created request is the obvious suspect, but this run does not measure it. It needs its own timer before the number can be claimed.

Checks the run had to pass

The harness refuses to emit a summary unless the native NPUW log proves the run did what it claims. All four gates passed.

GateResult
switch_proof1 switch expected, 1 observed; none missing, unexpected, or duplicated

boundary_logits_completelogits captured either side of the switch

The boundary logits are the correctness check. If the copy dropped or reordered any KV, the logits after the switch would diverge. They are stored so the lazy run can be compared against them bit for bit.

What this sets up

The eager arm is not interesting on its own — it is the zero point. It says: with compilation entirely out of the way, growing a KV cache from 1024 to 2048 costs one 764 ms hiccup and 12.0 ms per token afterwards.

The lazy arm compiles the second variant during decode instead. Against this baseline, two questions have clean answers: does the background compile slow the tokens it overlaps, and does the variant arrive before token 895. Here the answers are known to be no and yes — by construction. Anything worse is what laziness costs.
